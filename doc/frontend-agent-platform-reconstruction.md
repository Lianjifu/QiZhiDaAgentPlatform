# 面向中小企业的企业级智能体平台前端重构方案

> 文档状态：设计提案
>
> 适用范围：`frontend/web` 及 `frontend/packages/ui`、`frontend/packages/api`
>
> 目标产品：面向中小企业的智能体工作平台，兼顾业务使用、智能体建设、运营管理与安全治理。

---

## 1. 目标与设计原则

### 1.1 产品定位

本平台不是面向 AI 专家的模型控制台，而是中小企业可以直接使用的 **企业智能体工作平台**：

- 员工可以用自然语言完成工作；
- 业务负责人可以搭建和发布智能体、流程与知识库；
- 管理员可以控制成员、权限、用量、成本和安全；
- 企业可以追踪每次执行的结果、来源和责任。

平台需要同时满足两种心智模型：

| 使用者 | 他们真正关心的问题 |
|---|---|
| 普通员工 | “我想完成这件事，哪个智能体能帮我？” |
| 业务负责人 | “我如何把重复工作交给智能体？” |
| 管理员 | “平台是否稳定、可控、可追溯？” |
| 审计/安全人员 | “谁在什么时间访问了什么数据，做了什么操作？” |

### 1.2 重构原则

1. **先按用户任务组织导航，再按技术模块组织后台。**
2. **用户侧不暴露模型、Provider、Token、MCP、路由权重等技术概念。**
3. **管理侧以“建设、运行、治理”组织功能，不把所有配置堆在一个设置页面。**
4. **默认路径优先服务非专业用户，专业能力通过渐进式披露出现。**
5. **同一个概念只保留一个产品名称。** 统一使用“智能体”，避免旧称与“智能体”并列造成理解成本。
6. **页面是组合层，业务能力归属 feature，通用能力归属 shared。**
7. **不以一次性重写为目标，按领域逐步迁移并保持可回滚。**
8. **任何重要结果都应具备来源、状态、责任人和下一步操作。**

## 2. 产品信息架构

平台采用一个身份体系、两个工作空间、两套导航壳层：

```text
企业智能体平台
├── 智能体工作台（用户侧）
│   ├── 首页
│   ├── 智能体广场
│   ├── 对话与任务
│   ├── 知识问答
│   ├── 自动化流程
│   ├── 团队协作
│   └── 效果看板
│
└── 管理控制台（管理侧）
    ├── 概览
    ├── 建设
    ├── 配置
    ├── 运行
    ├── 治理
    ├── 组织与账户
    ├── 系统设置
    └── 运营支持
```

### 2.1 两套导航的切换

拥有管理权限的用户在顶部工作区切换器旁看到：

- `进入管理控制台`
- `返回智能体工作台`

普通成员永远只看到用户侧导航。管理员可以默认进入管理控制台，也可以在个人设置中选择默认入口。

### 2.2 统一的工作空间上下文

平台所有页面都应明确当前工作空间：

```text
企业名称 / 工作空间名称 / 当前页面
```

切换工作空间时：

- 清理或重新请求当前工作空间的数据；
- 保留语言、主题等个人偏好；
- 不允许出现跨工作空间的列表混合；
- 对正在执行的任务显示切换提示；
- 页面和 API 请求统一携带 workspace context。

## 3. 用户侧：智能体工作台

用户侧面向普通员工、业务执行人员、团队负责人。导航语言应接近办公软件，而不是开发平台。

### 3.1 用户侧一级菜单

用户侧围绕四个连续的问题组织：

1. **协作**：我现在要让智能体做什么？
2. **任务**：有哪些事情正在执行、需要我处理？
3. **能力**：我可以使用或创建哪些智能体、知识和自动化？
4. **结果**：这次执行产生了什么，带来了什么价值？

因此，用户侧采用场景型导航，而不是按技术模块拆分：

```text
首页
智能体广场
对话与任务
知识问答
自动化流程
团队协作
效果看板
```

辅助入口放在侧栏底部或右上角个人菜单：

```text
当前工作空间
帮助与教程
个人中心
```

“个人中心”不参与主要工作流，不承载会话、任务、知识和产出物等业务内容。

### 3.2 首页

路径：`/home`

首页回答两个问题：

1. 我今天需要处理什么？
2. 我可以让什么智能体帮我完成？

页面区域：

```text
首页
├── 快捷开始
│   ├── 新建对话
│   ├── 运行智能体
│   ├── 发起流程
│   └── 搜索知识
├── 待我处理
│   ├── 待办任务
│   ├── 待审批事项
│   └── 失败待重试
├── 最近使用
│   ├── 最近会话
│   ├── 最近智能体
│   └── 最近流程
├── 团队推荐
│   └── 团队常用智能体与知识
└── 通知
```

首页不展示复杂的模型调用量、系统健康指标和后台配置。用户可以看到与自己工作直接相关的状态。

### 3.3 智能体广场

路径：

```text
/agents
/agents/:agentId
/agents/mine
/agents/templates
/agents/new
```

智能体广场回答：

> 我现在可以使用什么能力？有没有现成模板？我能不能自己创建一个？

子页面：

```text
智能体广场
├── 场景浏览
├── 官方模板
├── 团队智能体
├── 我创建的智能体
└── 新建智能体
```

按业务场景浏览：

```text
场景分类
├── 客服应答
├── 文案创作
├── 数据分析
├── 行政办公
├── 销售支持
├── 人事与招聘
├── 财务与采购
├── 法务与合规
└── 企业通用
```

“新建智能体”面向业务用户采用向导式创建：

1. 选择场景和目标；
2. 描述希望智能体完成的工作；
3. 选择知识资料；
4. 选择可用工具和输出格式；
5. 使用样例任务测试；
6. 保存为个人草稿或提交团队发布。

用户侧可以创建轻量个人智能体，但涉及共享、外部写入、敏感数据和自动执行时，必须进入审批或管理发布流程。

### 3.4 对话与任务

路径：

```text
/copilot
/copilot/:conversationId
/copilot/shared
/copilot/artifacts
/tasks
/tasks/:taskId
```

对话与任务是用户侧最核心的执行入口，回答：

> 我想让智能体完成一件事，现在进行到哪里，结果在哪里？

子页面：

```text
对话与任务
├── 新建对话
├── 历史会话
├── 任务型执行记录
├── 收藏与标签
└── 产出物
```

核心功能：

- 选择已授权智能体并描述目标；
- 上传文件或引用知识；
- 查看智能体的执行步骤和当前状态；
- 处理人工确认和审批；
- 查看来源、引用和执行结果；
- 下载、收藏、标记和分享产出物。

用户看到“正在分析资料”“需要你的确认”“已生成报告”等业务状态，不直接暴露 SSE、tool call、Provider 或模型 fallback 等实现概念。

### 3.4.1 任务型执行记录与待办

任务列表属于“对话与任务”的子入口，不作为独立一级菜单。



```text
/tasks
/tasks/pending
/tasks/approvals
/tasks/created
/tasks/completed
/tasks/failed
```

子菜单：

```text
任务型执行记录
├── 待我处理
├── 待我审批
├── 我发起的
├── 已完成
└── 失败与异常
```

任务卡片必须包含：

- 任务名称；
- 来源智能体或流程；
- 当前状态；
- 下一步操作；
- 截止时间；
- 风险或敏感数据提示；
- 发起人和责任人；
- 关联会话、流程和产出物。

用户侧不显示完整技术日志，详情中提供“查看执行记录”入口供有权限的用户查看。

### 3.5 知识问答

路径：

```text
/knowledge
/knowledge/ask
/knowledge/upload
/knowledge/mine
/knowledge/sources
```

知识问答回答：

> 我能不能基于企业资料直接得到可信答案？

子页面：

```text
知识问答
├── 开始问答
├── 上传资料
├── 我的知识库
├── 已连接数据源
└── 最近引用
```

用户侧能力：

- 上传文档、表格和图片；
- 对资料进行问答和摘要；
- 查看原文、来源和引用位置；
- 管理自己的知识资料；
- 连接被授权的网盘、飞书、钉钉文档、CRM 等数据源；
- 对答案的准确性和帮助程度反馈。

用户侧不显示索引分片、embedding、向量库、chunk 等实现术语。数据源连接需要明确展示访问范围、同步状态和断开操作。

### 3.6 自动化流程

自动化流程回答：

> 哪些重复工作可以自动触发并持续执行？

路径：

```text
/automations
/automations/:automationId
/automations/new
/automations/runs
/automations/runs/:runId
```

子菜单：

```text
自动化流程
├── 我的自动化
├── 新建自动化
├── 进行中
└── 执行记录
```

用户侧可以通过可视化方式配置：

- 触发条件，例如表单提交、定时、消息或数据变化；
- 执行动作，例如调用智能体、生成文件、发送通知或更新业务系统；
- 人工确认节点；
- 失败重试、超时和通知策略；
- 执行结果和产出物。

涉及跨团队共享、外部写入、敏感数据或高频自动执行时，需要提交审核。流程设计器、版本、发布和环境配置由管理侧负责。

### 3.7 团队协作

团队协作回答：

> 如何让团队共享智能体、知识和执行结果，而不是每个人重复配置？

路径：

```text
/team
/team/agents
/team/knowledge
/team/activity
```

子页面：

```text
团队协作
├── 团队空间
│   ├── 共享智能体
│   ├── 共享知识库
│   └── 共享自动化
├── 成员动态
└── 团队产出物
```

团队空间必须明确：

- 谁可以查看、使用、编辑和发布；
- 内容属于个人、团队还是企业；
- 成员动态是否可见；
- 共享智能体和知识库的负责人；
- 离职或成员移除后的资源归属。

团队负责人可以看到团队聚合数据，但不能默认查看成员的私人会话内容。私人会话只有在主动分享、授权审计或安全事件调查时才可访问。

### 3.8 效果看板

效果看板回答：

> 智能体是否真正帮我和团队节省了时间、完成了工作？

路径：`/insights`

子页面：

```text
效果看板
├── 我的使用小结
├── 团队使用统计
├── 任务完成率
├── 节省时长估算
└── 满意度与反馈
```

展示指标应优先采用业务语言：

- 本周完成的智能体任务数；
- 预计节省时长；
- 任务完成率和人工接管率；
- 常用智能体和自动化；
- 反馈满意度；
- 失败、重试和待优化事项。

个人成员默认只能查看自己的统计。团队负责人查看聚合数据，管理员在管理侧运行和治理模块查看全平台数据。所有“节省时长”必须标注为估算值，并说明计算口径。

### 3.9 个人中心与账户入口

个人中心是辅助入口，不承载业务资源。

路径：`/account`

```text
个人中心
├── 个人资料
├── 账号安全
├── 通知设置
├── 使用记录
├── 偏好设置
└── 帮助与教程
```

会话、任务、智能体、知识、流程和产出物必须留在各自业务菜单中，不放入个人中心。

### 3.10 内容归属原则

用户侧不设置“我的空间”一级页面，也不为了收纳零散功能建立一个“我的”容器。个人内容按照用户任务归入对应模块：

| 内容 | 所属位置 |
|---|---|
| 会话、收藏会话、产出物 | 对话与任务 |
| 待办、审批、我发起的任务 | 对话与任务中的任务区 |
| 收藏智能体、最近使用、个人草稿 | 智能体广场 |
| 我发起的自动化、执行历史 | 自动化流程 |
| 我的资料、最近引用 | 知识问答 |
| 团队共享内容、成员动态 | 团队协作 |
| 个人资料、账号安全、通知和偏好 | 个人中心 |

个人中心入口可放在右上角头像菜单或侧栏底部；桌面端不必把它作为工作导航的核心一级入口。

## 4. 管理侧：管理控制台

管理侧面向管理员、业务构建者、平台运营、安全人员和审计员。它不只是“系统设置”，而是企业智能体能力的建设与运营中心。

### 4.1 管理侧一级菜单

管理侧围绕四个连续的问题组织：

1. **建设**：智能体、知识、工具和应用如何被创建出来？
2. **配置**：模型、额度、权限和业务规则如何被统一配置？
3. **运行**：已发布能力是否稳定、可用、成本可控？
4. **治理**：数据、内容、操作和风险是否安全、合规、可追溯？

因此，管理侧采用领域分组导航：

```text
概览
├── 运营数据总览
└── 异常与告警中心

建设
├── 智能体与应用
├── 知识库建设
├── 自动化流程
└── 插件与工具

配置
├── 模型与算力
├── 额度与成本策略
├── 角色与权限
└── 业务规则

运行
├── 上架与发布
├── 运行监控
├── 告警配置
└── 成本与用量

治理
├── 内容安全
├── 审计日志
├── 数据安全与合规
└── 风险评估

组织与账户
├── 组织架构
├── 成员管理
└── 订阅与账单

系统设置
├── 品牌与界面
├── 通知与告警渠道
└── 开放平台与密钥

运营支持
├── 公告与消息推送
└── 工单与客服
```

下文的“智能体建设、流程管理、知识管理、模型与用量”等是实现子域，不代表额外的一级侧栏菜单。这样可以避免侧栏同时出现十几个技术模块。

### 4.2 概览

路径：`/admin/overview`

页面回答：

> 平台现在是否健康？哪些事情需要我处理？

区域：

```text
概览
├── 运行摘要
│   ├── 活跃成员
│   ├── 活跃智能体
│   ├── 流程运行量
│   ├── 成功率
│   └── 当前用量
├── 待处理事项
│   ├── 发布审批
│   ├── 权限申请
│   ├── 风险告警
│   └── 失败任务
├── 资源健康
│   ├── 模型服务
│   ├── 知识处理
│   ├── 渠道连接
│   └── 任务队列
└── 趋势与建议
```

中小企业通常没有专职平台运维人员，因此概览页需要直接给出“建议动作”，例如：

- “知识库有 12 份文档超过 90 天未更新”；
- “销售助手最近 7 天失败率升高”；
- “本月模型用量达到预算的 80%”；
- “有 3 个成员等待权限审批”。

### 4.3 组织与账户

路径：

```text
/admin/workspaces
/admin/members
/admin/teams
/admin/roles
/admin/quotas
```

子菜单：

```text
组织与账户
├── 工作空间
├── 成员
├── 团队
├── 角色与权限
├── 用量配额
└── 访问范围
```

功能：

- 创建和管理工作空间；
- 邀请、停用和移除成员；
- 设置团队；
- 分配角色；
- 配置数据访问范围；
- 配置团队默认智能体；
- 设置成员和团队配额。
- 管理套餐、订阅周期、发票和续费提醒；
- 展示当前套餐包含的成员数、智能体数、知识容量和用量额度；
- 对即将超额、订阅到期和付款失败给出明确提醒。

订阅与账单只对具备账户管理权限的管理员显示，普通成员不应看到企业付款信息。

角色不应只有技术权限，还应体现工作职责：

```text
平台管理员
智能体构建者
业务负责人
普通成员
审计员
只读成员
```

### 4.4 建设：智能体与应用

建设域回答：

> 企业需要的智能体、知识、工具和应用，如何被创建并交付给员工？

建设域包含四类资产：

```text
建设
├── 智能体模板与组件库
├── 知识库建设
├── 自动化流程
├── 插件与工具接入
└── 应用市场管理
```

- **模板与组件库**：管理官方模板、提示词模块、输出格式和可复用节点；
- **知识库建设**：负责接入、清洗、审核、加工和索引状态；
- **自动化流程**：负责流程设计、版本和发布前校验；
- **插件与工具接入**：负责 API、第三方系统和执行工具；
- **应用市场管理**：负责应用上下架、版本、可见范围和发布说明。

路径：

```text
/admin/agents
/admin/agents/new
/admin/agents/:agentId
/admin/agents/:agentId/design
/admin/agents/:agentId/knowledge
/admin/agents/:agentId/tools
```

## 6. 页面布局与交互规范

### 6.1 用户侧布局

```text
┌──────────────────────────────────────────────────────┐
│ 菜单  Logo  工作空间              搜索  通知  用户    │
├──────────────┬───────────────────────────────────────┤
│ 用户侧导航   │ 面包屑 / 页面标题                       │
│              │ 页面操作                               │
│              ├───────────────────────────────────────┤
│              │ 内容区                                 │
│              │                                         │
└──────────────┴───────────────────────────────────────┘
```

用户侧原则：

- 一屏内能看懂下一步；
- 操作按钮使用动词，例如“开始协作”“运行流程”“申请访问”；
- 默认隐藏高级详情；
- 空状态必须提供下一步动作；
- 错误状态必须告诉用户如何恢复。

### 6.2 管理侧布局

```text
┌──────────────────────────────────────────────────────┐
│ 管理控制台  工作空间  全局搜索       帮助  用户       │
├──────────────┬───────────────────────────────────────┤
│ 管理侧导航   │ 面包屑 / 模块标题                       │
│              │ 页面级操作 / 筛选                       │
│              ├───────────────────────────────────────┤
│              │ 指标 / 表格 / 详情 / 操作面板            │
└──────────────┴───────────────────────────────────────┘
```

管理侧原则：

- 支持列表、筛选、批量操作和详情抽屉；
- 所有危险操作需要说明影响范围；
- 列表状态统一为加载、空、错误、无权限；
- 重要配置显示生效范围、更新时间和修改人；
- 复杂对象使用详情页或分步向导，不把所有字段塞进弹窗。

### 6.3 响应式策略

统一断点：

| 模式 | 宽度 | 导航行为 |
|---|---:|---|
| 手机 | `< 768px` | 侧栏变抽屉，内容单列 |
| 平板 | `768–1023px` | 侧栏可折叠，详情使用抽屉 |
| 桌面 | `1024–1279px` | 侧栏固定，详情按需展开 |
| 宽屏 | `>= 1280px` | 支持列表 + 主内容 + 详情三列 |

Copilot 的会话列表、主区、上下文区应使用统一响应式策略：

- 手机：主区 + 抽屉；
- 平板：主区 + 单侧详情；
- 桌面：会话列表 + 主区；
- 宽屏：会话列表 + 主区 + 上下文。

页面不得自行维护不一致的 `window.innerWidth` 阈值。

## 8. 页面迁移顺序

### 阶段一：应用壳层和导航

范围：

- 新增用户侧和管理侧导航模型；
- 拆分 `AppLayout`；
- 建立 `UserAppShell` 和 `AdminAppShell`；
- 统一路由配置和权限；
- 增加工作空间上下文；
- 保持旧页面路径兼容跳转。

验收：

- 不同角色看到正确菜单；
- 管理员可以在两套壳层间切换；
- 移动端抽屉、键盘和返回行为正常；
- 工作空间切换不串数据。

### 阶段二：对话与任务

范围：

- `CopilotPage` 迁移为对话与任务组合壳；
- 拆分 session、conversation、composer、approval、artifact、details；
- 拆分 `useChat` 为 transport、domain、persistence、UI；
- 统一 SSE、反馈、预览和分享 API；
- 补页面级集成测试。

验收：

- 新建会话、流式回复、审批、文件、分享全部可用；
- 移动端可以在会话、主区和上下文之间切换；
- 刷新页面后会话和草稿行为一致；
- 失败可恢复，不出现静默丢失。

### 阶段三：智能体广场与团队协作

范围：

- 将 Digital Employees 统一为智能体广场和智能体建设；
- 用户侧增加场景分类、官方模板、个人草稿和团队共享；
- 管理侧增加模板、组件、创建向导、版本和应用发布；
- 增加团队空间、共享资源和成员动态；
- 将个人、团队和企业资源的归属与可见范围明确化。

验收：

- 普通用户只看到已授权、已发布的智能体；
- 构建者可以从创建到发布走完整流程；
- 发布版本可回滚；
- 团队共享资源有明确负责人和访问范围；
- 权限变更有审计记录。

### 阶段四：知识问答与自动化流程

范围：

- 拆分自动化流程的用户运行、管理设计和运行实例；
- 拆分知识问答的问答、资料、数据源和管理建设边界；
- 建立统一列表、过滤、详情、执行状态和产出物组件；
- 增加效果看板的个人、团队和平台指标边界。

验收：

- 用户可以发起和跟踪自动化流程；
- 管理员可以设计、测试、发布自动化流程；
- 知识来源、加工、索引、权限和引用可追踪；
- 个人和团队效果指标不会越权混合。

### 阶段五：配置、运行、治理与运营支持

范围：

- 将 Models、Providers、Routing 收敛到“配置 / 模型与算力”；
- 将 Channels、Connectors、MCP 收敛到“建设 / 插件与工具”；
- 将 ZeroTrust、Governance、Access Control 收敛到“治理”；
- 增加订阅、账单、套餐、公告和工单能力；
- 区分概览发现、运行定位、治理追责和运营支持；
- 收敛 Settings 为系统级默认设置。

验收：

- 管理员可以完成组织、模型、渠道、安全和审计闭环；
- 每个配置显示生效范围、修改人和更新时间；
- 高风险操作可审批、可追踪、可回滚。

## 10. 兼容与迁移策略

1. **旧路径先保留跳转。**
   - `/partners` 跳转到 `/agents`；
   - `/workflows` 跳转到 `/automations`；
   - `/governance` 跳转到 `/admin/governance`；
   - `/zero-trust` 跳转到 `/admin/governance/security`；
   - `/audit-center` 跳转到 `/admin/audit`；
   - `/models`、`/channels`、`/settings` 分别跳转到新的管理分组页面。
2. **旧组件和新组件短期并存。** 每次只迁移一个完整领域。
3. **先迁导航和数据边界，再迁视觉。** 避免视觉改版掩盖状态和权限问题。
4. **旧 localStorage key 只保留明确的迁移读取。** 新代码不继续写入旧 key。
5. **每个阶段独立提交和可回滚。** 不把所有页面重构放入一个不可回滚的大提交。
6. **发布前使用角色矩阵回归。** 至少验证普通成员、构建者、管理员、审计员四种身份。

## 12. 结论

面向中小企业的智能体平台，最重要的不是把更多 AI 技术放进菜单，而是让用户可以用熟悉的办公方式完成三件事：

1. **使用智能体完成工作；**
2. **把重复工作建设成智能体和流程；**
3. **让平台可控、可运营、可追溯。**

因此，前端重构应采用“用户侧智能体工作台 + 管理侧控制台”的双壳层架构：

- 用户侧围绕“协作、任务、能力、结果”组织；
- 管理侧围绕“建设、配置、运行、治理”组织；
- 首页提供个人工作入口和使用小结，效果看板呈现业务价值；
- 团队协作承载共享资源，但不替代个人业务模块；
- 概览负责发现问题，运行负责定位问题，治理负责追责和改进；
- 共享身份、工作空间、设计系统和数据访问基础设施；
- 不共享混杂的导航和页面职责。

实施顺序建议固定为：

```text
导航与壳层
→ 路由与权限
→ API 与 workspace 数据边界
→ 对话与任务
→ 智能体广场
→ 自动化流程与知识问答
→ 配置、运行与治理
→ 测试与质量门禁
```

这套结构既保留企业级平台所需要的治理能力，也避免中小企业用户一登录就面对模型、路由、密钥和审计等技术复杂度。
